# CameoDB Distributed Implementation Plan

## ➕ 2025-12-04 Update: Custom Swarm Roadmap

Recent analysis shows that relying on `remote::bootstrap()` (even with interface filtering) keeps
libp2p mDNS bound to every interface, which conflicts with VPN/tunnel adapters and prevents the
production-grade controls we need. The new implementation path replaces the convenience bootstrap
with an explicit swarm composition that we own end-to-end.

### Phase A: Swarm Infrastructure
1. **Behaviour module** – Build `DistributedBehaviour` combining `remote::Behaviour` with a filtered
   mDNS (or alternative discovery) provider. Expose hooks for adding more protocols later.
2. **Filtered provider** – Implement `FilteredMdnsProvider` (wraps `if_watch::tokio::IfWatcher`) to
   drop events for tunnel/bridge/VPN interfaces before libp2p spawns sockets.
3. **Swarm builder** – Mirror the production example:
   - Configure TCP (`port_reuse`, `nodelay`) and QUIC transports.
   - Apply swarm-level tuning (idle timeout, stream negotiation limits).
   - Support multiple listen addresses from config (tcp + quic).
4. **Bootstrap peers** – Dial configured multiaddrs (with `/p2p/<PeerId>` suffix). Accept empty list
   for single-node/dev deployments.
5. **Event loop** – Spawn a dedicated task that polls `Swarm::select_next_some()` and surfaces
   connection events via tracing/logging.

### Phase B: Integration with DistributedCluster
1. `DistributedCluster::init_swarm()` – Async entry that builds the swarm, calls
   `behaviour.kameo.init_global()`, then spawns the event loop task. Persist the local `PeerId`.
2. Maintain swarm ownership inside `DistributedCluster` (e.g., `Arc<Mutex<Swarm<DistributedBehaviour>>>`
   or a command channel) for dial/listen updates and shutdown coordination.
3. Provide helper methods to dial bootstrap peers, refresh listen addresses, and publish discovery
   metadata as the cluster topology evolves.
4. Keep shard registration/lookup APIs but route them through the new swarm abstractions.

### Phase C: Configuration & UX
1. Extend `ClusterConfig` / `cameodb.toml` with:
   - `listen_addrs`: list of multiaddrs (tcp/quic) to bind.
   - `bootstrap_peers`: list of remote multiaddrs (with peer IDs).
   - `messaging` tuning (request timeout, max concurrent requests).
   - `mdns_enabled` flag and optional allow/deny filter patterns.
2. Update startup logs to enumerate chosen transports, listen addresses, filtered interfaces, and
   bootstrap peers for operator clarity.

### Phase D: Follow-on Enhancements
1. Optional: expose admin endpoint or CLI to manage bootstrap peers and listen addresses at runtime.
2. Optional: surface swarm metrics (active peers, dial failures, mDNS status) for observability.
3. Optional: integrate alternative discovery strategies (DNS, static peer lists) when mDNS is disabled.

## Phase 1: Swarm Infrastructure Implementation

### 1.1 Create Behaviour Module
- Define `DistributedBehaviour` combining `kameo::remote::Behaviour` with filtered mDNS (or optional
  null discovery when disabled).
- Expose builder helpers to attach additional libp2p behaviours later (Kademlia, gossip, etc.).

### 1.2 Implement Filtered mDNS Provider
- `FilteredMdnsProvider` wraps `if_watch::tokio::IfWatcher`, filters events based on interface name
  patterns (utun, tun, tap, bridge, docker, veth) and address families.
- Allow configuration-driven allow/deny overrides.

### 1.3 Build Swarm Factory
- `swarm::build(config: &ClusterConfig) -> anyhow::Result<Swarm<DistributedBehaviour>>` that:
  - Applies TCP (`port_reuse`, `nodelay`) and QUIC transports.
  - Sets swarm config (`idle_connection_timeout`, `max_negotiating_inbound_streams`).
  - Calls `remote::Behaviour::new(peer_id, messaging_config)` with tuned request settings.
  - Attaches filtered mDNS when enabled.
  - Listens on all configured `listen_addrs`.

### 1.4 Event Loop Task
- Spawn `Swarm` driver task that:
  - Logs `SwarmEvent` variants (connections, errors, discovery).
  - Routes discovery events back into `DistributedCluster` (update peer registry, shard metadata).
  - Handles shutdown via watch channel or swarm command queue.

## Phase 2: DistributedCluster Integration

### 2.1 Store Swarm Handles
- Keep `Arc<Mutex<Swarm<DistributedBehaviour>>>` plus command channel for dial/listen requests.
- Persist local `PeerId` and listen addresses for API exposure / logging.

### 2.2 Initialization Flow
- Replace `bootstrap_with_config()` with `init_swarm()` that:
  - Builds the swarm via Phase 1 factory.
  - Calls `behaviour.kameo.init_global()`.
  - Spawns the driver task.
  - Returns `PeerId` for logging/API.

### 2.3 Peer & Shard Coordination
- Update shard registration/lookup to use `remote::ActorSwarm::get()` (already initialised by
  custom swarm).
- Maintain peer metadata from swarm events (connected addresses, statuses) in `peer_nodes` map.
- Provide `dial_bootstrap_peers()` that iterates configured peers and sends dial commands to swarm.

## Phase 3: NodeOrchestrator & Router Updates

### 3.1 Orchestrator Wiring
- Ensure orchestrator holds `Arc<RwLock<DistributedCluster>>` and calls `init_swarm()` during startup.
- After local shard startup, register actors with Kameo registry (unchanged API).

### 3.2 Router Remote Routing
- Continue using `DistributedCluster::lookup_remote_shard()` but have it rely on
  `RemoteActorRef::lookup` / cached references initialised post-swarm.
- Add resilience: if remote lookup fails, trigger swarm dial attempt before returning error.

## Phase 4: Discovery & Topology Management

### 4.1 Configurable Discovery
- mDNS: enable filtered provider when `mdns_enabled = true`.
- Static bootstrap: dial configured peers at startup and allow runtime refresh.
- Future: optional DNS-based discovery or HTTP registry integration.

### 4.2 Peer Health Tracking
- From swarm loop, update `NodeStatus` to Connected/Disconnected based on events.
- Provide admin API or CLI to inspect current peer table, listen addrs, peer IDs.

## Phase 5: Search & Query Distribution
- Keep existing cross-node search plan but ensure remote shard lookups integrate with new swarm
  metadata (peer availability, latencies).
- Consider caching remote shard actor refs with TTL invalidation when peers disconnect.

## Phase 6: Operational Enhancements
- Expose metrics/telemetry (peer counts, dial failures, request latencies).
- Allow dynamic configuration reload for listen addresses, bootstrap peers.
- Provide tooling to gracefully drain nodes (inform peers before shutdown).

## Next Steps (Execution Checklist)
- **Phase 1 – Swarm infrastructure**: implement behaviour module, filtered provider, swarm factory, and driver task.
- **Phase 2 – DistributedCluster integration**: wire custom swarm into cluster lifecycle and expose peer-management helpers.
- **Phase 3 – Orchestrator & router**: ensure routing logic leverages custom swarm and adds retry/dial resilience.
- **Phase 4 – Discovery & topology**: finalize mDNS/static bootstrap configuration, peer health tracking, and visibility tooling.
- **Phase 5 – Query distribution**: align search and write routing with swarm-managed remote shards.
- **Phase 6 – Operations**: add metrics, dynamic config reload, and graceful drain workflows.
