# CameoDB Distributed Implementation Plan

## Current Baseline (Completed)

- **Networking**: Custom `DhtBehaviour` (Kameo remote behaviour + Kademlia + keep-alive) with TCP/QUIC/Noise/Yamux transport stack and metrics-aware runtime task implemented in `swarm/mod.rs`.
- **Swarm lifecycle**: `init_distributed_swarm` returns `SwarmStartup` + `SwarmRuntimeHandle`; graceful shutdown supported via `watch::Sender`.
- **Configuration**: `ClusterConfig` exposes `cluster_port`, `bootstrap_nodes`, optional `bootstrap_peers`, and all critical values can be overridden via `CAMEODB_*` environment variables (used by Docker Compose).
- **DistributedCluster**: Initializes the swarm, retains runtime handle, logs cluster status, and seeds `peer_nodes` from bootstrap configuration.
- **Documentation & Compose**: README/docker guides updated for Kademlia-only discovery; no mDNS dependency remains.

These pieces deliver a stable Kademlia-only networking layer that can be deployed via Docker Compose with deterministic bootstrap peers.

## Guiding Principles

1. **Actor-first design**: All distributed coordination must flow through Kameo actors to preserve isolation, avoid manual locking, and leverage remote actor features.
2. **Blocking I/O offloading**: Every redb/tantivy access remains behind `tokio::task::spawn_blocking`.
3. **Strong typing & observability**: Prefer structured enums/structs over ad-hoc JSON, and emit tracing metrics for cluster visibility.

## Roadmap (Actor-Oriented)

### Phase 3 – Cluster Coordinator Actor
- Introduce a `ClusterCoordinator` (Kameo actor) that wraps `DistributedCluster`.
- Messages: `InitSwarm`, `ShutdownSwarm`, `DiscoverPeers`, `GetStatus`, `RouteShard` (stub until remote actors arrive).
- Startup flow: spawn the actor during node boot, await `InitSwarm`, and handle errors by falling back to single-node mode.
- Retain the `SwarmRuntimeHandle` inside the actor and trigger shutdown in `Drop` or explicit `ShutdownSwarm`.

### Phase 4 – Router Integration
- Update HTTP/router handlers to communicate with `ClusterCoordinator` instead of owning the cluster directly.
- Implement request helpers that forward routed reads/writes through the actor (local handling continues to use existing `RouterActor` + `NodeOrchestrator`).
- Stub retry hooks (e.g., `RequestBootstrapRedial`) for future resilience when remote shard lookup fails.

### Phase 5 – Topology & Peer Tracking (Implemented)
- Swarm runtime emits `CoordinatorEvent` channel carrying `RoutingUpdated`, `PeerDiscovered`, `PeerLost`, `DialFailed`.
- `ClusterCoordinator::InitSwarm` spawns a forwarder task to translate swarm events into actor messages.
- `DistributedCluster` tracks peer map and counters (bootstrap successes, dial failures, routing updates); `GetStatus` exposes peer/counter data.

### Phase 6 – Shard Registration & Token Ownership (Implemented locally)
- `NodeOrchestrator` registers hydrated/created shards with `ClusterCoordinator` using `RegisterLocalShards` and `ShardMetadata`.
- Coordinator tracks shard assignments and rebuilds a local consistent ring for routing decisions.
- Storage stats remain stubbed; replication of shard metadata to peers is still future work.

### Phase 7 – Query & Write Distribution
- TODO: Implement remote read/write flows using coordinator routing decisions and Kameo remoting for microshards.
- TODO: Use consistent ring for routing_key lookups; add tests for even token distribution across nodes.
- TODO: Add scatter-gather helpers for broadcast searches when `routing_key` is absent (local shards now; remote later).

### Phase 8 – Operational Enhancements
- Admin/observability: HTTP endpoints or CLI commands that query the coordinator actor for peer/shard state.
- Dynamic configuration: allow updating bootstrap nodes, discovery policies, or shard assignments through actor commands.
- Graceful drains: coordinator notifies peers before shutdown, using swarm handle + node orchestration messages.

## Phase 4.5 – NodeOrchestrator Actor Migration (Arc<RwLock> Elimination)

This is a two-commit refactoring to eliminate `Arc<RwLock<NodeOrchestrator>>` from `RouterActor`:

### Commit 1 (Completed)
- ✅ Added message types: `GetShardCount`, `GetIdentity`, `GetShardIds`
- ✅ Added `#[derive(Actor)]` to `NodeOrchestrator`
- ✅ Added `NodeIdentityInfo` reply type with `Reply` derive
- ✅ Added Message handlers for `GetShardCount`, `GetIdentity`, `GetShardIds`, `ProposeShard`
- **Existing RouterActor preserved** - still uses `Arc<RwLock<NodeOrchestrator>>`

### Commit 2 (Pending)
- [ ] Add `Message<ClientOp>` handler to `NodeOrchestrator` that delegates to new `handle_client_op` method
- [ ] Add operation handlers to NodeOrchestrator: `orch_write`, `orch_bulk_write`, `orch_search`, etc.
- [ ] Update `RouterActor` struct: `orchestrator: ActorRef<NodeOrchestrator>` (remove `Arc<RwLock>`)
- [ ] Simplify `RouterActor::handle_client_op` to just forward via `self.orchestrator.ask(op).await`
- [ ] Delete old RouterActor methods (~700 lines)
- [ ] Update `main.rs`: spawn `NodeOrchestrator` as actor, pass `ActorRef` to `RouterActor`
- [ ] Update `http_server.rs`: remove `orchestrator: Arc<RwLock<>>` from `AppState`

**Benefits after Commit 2:**
- No locks needed for orchestrator access
- Clean actor hierarchy: HTTP → RouterActor → NodeOrchestrator → MicroshardActors
- Aligns with "Actor-first design" principle
