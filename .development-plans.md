# CameoDB Distributed Implementation Plan

## ➕ 2025-12-04 Update: Custom Swarm Roadmap

Recent analysis shows that relying on `remote::bootstrap()` (even with interface filtering) keeps
libp2p mDNS bound to every interface, which conflicts with VPN/tunnel adapters and prevents the
production-grade controls we need. The new implementation path replaces the convenience bootstrap
with an explicit swarm composition that we own end-to-end.

### Phase A: Swarm Infrastructure
1. **Behaviour module** – Build `DhtBehaviour` that composes `remote::Behaviour`, libp2p Kademlia,
   and `keep_alive`, keeping the API surface ready for future protocol add-ons.
2. **Transport stack** – Configure TCP (`port_reuse`, `nodelay`) and QUIC transports alongside Noise
   and Yamux, matching production requirements.
3. **Bootstrap peers** – Accept IP:port bootstrap entries, convert them to multiaddrs, and dial them
   on startup. Handle empty lists gracefully for standalone deployments.
4. **Event loop** – Spawn a dedicated runtime task that polls `Swarm::select_next_some()`, maintains
   metrics, and supports graceful shutdown via control channel.

### Phase B: Integration with DistributedCluster
1. `DistributedCluster::init_swarm()` – Async entry that builds the swarm, calls
   `behaviour.kameo.init_global()`, then spawns the event loop task. Persist the local `PeerId`.
2. Maintain swarm ownership inside `DistributedCluster` (e.g., `Arc<Mutex<Swarm<DistributedBehaviour>>>`
   or a command channel) for dial/listen updates and shutdown coordination.
3. Provide helper methods to dial bootstrap peers, refresh listen addresses, and publish discovery
   metadata as the cluster topology evolves.
4. Keep shard registration/lookup APIs but route them through the new swarm abstractions.

### Phase C: Configuration & UX
1. Extend `ClusterConfig` / `cameodb.toml` with:
   - `bootstrap_nodes`: list of IP:port entries for deterministic discovery.
   - `bootstrap_peers`: optional full multiaddrs (with peer IDs) for advanced setups.
   - `messaging` tuning (request timeout, max concurrent requests).
   - Environment variable overrides (`CAMEODB_*`) for container orchestration.
2. Update startup logs to enumerate transports, listen addresses, cluster name, and bootstrap peers
   for operator clarity.

### Phase D: Follow-on Enhancements
1. Optional: expose admin endpoint or CLI to manage bootstrap peers and listen addresses at runtime.
2. Optional: surface swarm metrics (active peers, dial failures, routing table changes) for
   observability.
3. Optional: integrate alternative discovery strategies (DNS, static peer lists) to complement the
   Kademlia bootstrap path.

## Phase 1: Swarm Infrastructure Implementation

### 1.1 Create Behaviour Module
- Define `DhtBehaviour` combining `kameo::remote::Behaviour`, libp2p Kademlia, and
  `keep_alive::Behaviour`.
- Provide constructors that select Kademlia server mode and expose hooks for future protocol add-ons.

### 1.2 Compose Swarm Builder
- `create_production_swarm(config: &ClusterConfig) -> anyhow::Result<SwarmStartup>` that:
  - Applies TCP (`port_reuse`, `nodelay`) and QUIC transports.
  - Configures swarm-level tuning (`idle_connection_timeout`, `max_negotiating_inbound_streams`).
  - Calls `remote::Behaviour::new(peer_id, messaging_config)` with production timeouts.
  - Listens on the preferred address derived from `cluster_port`.

### 1.3 Bootstrap Workflow
- Accept `bootstrap_nodes` as IP:port strings; convert to multiaddr and dial each entry.
- Optionally honour `bootstrap_peers` full multiaddrs for advanced scenarios.
- Initiate Kademlia `bootstrap` when peers are successfully dialled; fallback to standalone mode when list is empty.

### 1.4 Swarm Runtime Task
- Spawn a Tokio task that drives `Swarm::select_next_some()` and records metrics.
- Support controlled shutdown via a `watch::Sender<SwarmControl>` stored on `SwarmRuntimeHandle`.
- Emit detailed tracing output for connection lifecycle, Kademlia events, and runtime summary.

## Phase 2: DistributedCluster Integration

### 2.1 Store Swarm Handles
- Persist the local `PeerId`, listen address, and bootstrap peer count returned by `SwarmStartup`.
- Store an optional `SwarmRuntimeHandle` used for shutdown and lifecycle inspection.
- Maintain `peer_nodes` map for discovered nodes (initially from bootstrap entries).

### 2.2 Initialization Flow
- Replace `bootstrap_with_config()` with `init_swarm()` that:
  - Calls `init_distributed_swarm(&cluster_config)`.
  - Logs cluster name, listen address, bootstrap stats, and discovery mode.
  - Retains the runtime handle for later shutdown.

### 2.3 Peer & Shard Coordination
- Provide `discover_peers()` that seeds `peer_nodes` using configured bootstrap nodes until live
  swarm events are wired in.
- Keep shard registration/lookup APIs ready for remote actor integration once available.

## Phase 3: NodeOrchestrator & Router Updates

### 3.1 Orchestrator Wiring
- Ensure `NodeOrchestrator` owns an `Arc<RwLock<DistributedCluster>>` and awaits `init_swarm()` during
  startup.
- On failure, log with context and continue in single-node mode for graceful degradation.

### 3.2 Router Remote Routing
- Continue using `DistributedCluster::route_to_shard()` as the abstraction for distributed routing.
- Add retry logic that triggers bootstrap redial when remote shard lookup fails (future work).

## Phase 4: Discovery & Topology Management

### 4.1 Kademlia-Driven Discovery
- Wire Kademlia `RoutingUpdated` events into `ClusterStateActor` (future phase) for authoritative
  peer tracking.
- Support administrative refresh of bootstrap nodes to prompt re-dial.

### 4.2 Peer Health Tracking
- From the swarm runtime, update `NodeStatus` to Connected/Disconnected based on connection events.
- Provide admin tooling or API endpoints to inspect peer table, listen addresses, and routing metrics.

## Phase 5: Search & Query Distribution
- Keep existing cross-node search plan but ensure remote shard lookups integrate with swarm-managed
  peer metadata when remote actors arrive.
- Consider caching remote shard actor refs with TTL invalidation when peers disconnect.

## Phase 6: Operational Enhancements
- Expose metrics/telemetry (peer counts, dial failures, routing stats).
- Allow dynamic configuration reload for bootstrap nodes and discovery settings.
- Provide tooling to gracefully drain nodes (inform peers before shutdown) leveraging the runtime handle.

## Next Steps (Execution Checklist)
- **Phase 1 – Swarm infrastructure**: finalise `DhtBehaviour`, production swarm builder, bootstrap workflow, and runtime task.
- **Phase 2 – DistributedCluster integration**: hook the new swarm startup into cluster lifecycle and expose runtime handles.
- **Phase 3 – Orchestrator & router**: ensure routing logic leverages the swarm abstraction and prepares for remote shard lookups.
- **Phase 4 – Discovery & topology**: connect Kademlia events to `ClusterStateActor` and surface peer health.
- **Phase 5 – Query distribution**: align search/write routing with swarm-managed peers and remote actors.
- **Phase 6 – Swarm orchestration**: expand metrics, graceful shutdown, and operational tooling.


### Architecture Summary (Current State)

- Swarm behaviour: `DhtBehaviour` (Kameo remote behaviour + Kademlia + keep-alive)
- Discovery: Static/bootstrap peers via Kademlia; mDNS removed after evaluation
- Transport stack: TCP + QUIC + Noise + Yamux (Tokio executor)
- Runtime: Dedicated swarm task with watch-channel shutdown and metrics logging
- Configuration: `ClusterConfig` exposes `cluster_port`, `bootstrap_nodes`, env overrides
- Future work: Wire Kademlia events into `ClusterStateActor` and integrate remote actors for shard routing
Hybrid Discovery: Combining mDNS (local) and Kademlia DHT (global).
Actor-Based State: Syncing discovered peers into a Kameo Actor (ClusterState).

Phase 4: The Network Behaviour (behaviour.rs)
Requirement: Compose Kameo's behaviour with libp2p Kademlia for discovery.
Code Structure:
use kameo::remote::Behaviour as KameoBehaviour;
use libp2p::{kad, swarm::NetworkBehaviour, swarm::keep_alive};

#[derive(NetworkBehaviour)]
pub struct DhtBehaviour {
    // Core messaging
    pub kameo: KameoBehaviour,
    // Global discovery & storage
    pub kademlia: kad::Behaviour<kad::store::MemoryStore>,
    // Connection maintenance
    pub keep_alive: keep_alive::Behaviour,
}

Phase 6: Orchestration & Event Loop (mod.rs)
Requirement: The main entry point `init_distributed_swarm` which initializes the swarm and bridges events.
Logic Flow:
Init: Create SwarmBuilder with TCP + QUIC + Noise + Yamux.
Behaviour: Instantiate `DhtBehaviour`.
Config: Use Kademlia bootstrap peers sourced from config env variables.
Listen: Call utils::get_preferred_listen_address and swarm.listen_on(addr).
Loop: Spawn a Tokio task for swarm.select_next_some().
Event Handling Logic (Crucial):
Inside the loop match SwarmEvent::Behaviour(event):
Case Kademlia(RoutingUpdated):
If valid new peer, notify actor (future integration).
Case Kameo(...):
Log standard Kameo registry events and metrics.
Other SwarmEvents: Track metrics for runtime observability.
