# Contributing to CameoDB

## Documentation Guidelines

CameoDB maintains comprehensive documentation at multiple levels. Here's what should and shouldn't be committed to the repository:

### ✅ **DO Commit (Source Documentation)**

#### **Markdown Documentation**
- `docs/*.md` - Architecture, ADRs, and technical guides
- `README.md` files in crates and workspace root
- `CONTRIBUTING.md`, `CHANGELOG.md`, etc.

#### **Inline Code Documentation**
- `///` doc comments in Rust source code
- Code examples in doc comments
- Module-level `//!` documentation

#### **Configuration Documentation**
- `Cargo.toml` comments explaining dependencies
- Configuration file examples and templates

### ❌ **DON'T Commit (Generated Documentation)**

#### **Build Artifacts**
- `target/doc/` - Generated by `cargo doc`
- `target/` directory entirely (build artifacts)
- Any compiled binaries or libraries

#### **Generated Books**
- `book/` - Generated by mdbook
- `docs/book/` - If using mdbook for docs
- PDF exports or other generated formats

### 📚 **Documentation Commands**

```bash
# Generate and view API documentation
cargo doc --open --no-deps

# Generate documentation with private items (for development)
cargo doc --document-private-items --no-deps

# Test all documentation examples
cargo test --doc

# Check documentation links and examples
cargo doc --no-deps 2>&1 | grep -i warning
```

### 🚀 **Documentation Deployment**

Generated documentation should be deployed via CI/CD:

- **API Docs**: `cargo doc` output deployed to GitHub Pages
- **Architecture Docs**: Markdown files rendered by GitHub or docs site
- **Examples**: Maintained in source code and tested with `cargo test --doc`

### 📝 **Writing Guidelines**

1. **API Documentation**:
   - Every public function/struct must have `///` comments
   - Include `# Examples` sections with working code
   - Document error conditions and edge cases
   - Use `# Safety` sections for unsafe code

2. **Architecture Documentation**:
   - Use ADR (Architecture Decision Record) format
   - Include diagrams using Mermaid or ASCII art
   - Explain trade-offs and alternatives considered
   - Keep examples up-to-date with code changes

3. **Code Examples**:
   - All examples must compile and pass tests
   - Use `no_run` for examples that require setup
   - Use proper error handling in examples
   - Follow the centralized test data pattern

### 🔧 **Documentation Tools**

- **rustdoc**: Built-in Rust documentation generator
- **mdbook**: For book-style documentation (if needed)
- **Mermaid**: For diagrams in markdown
- **GitHub Pages**: For hosting generated docs

## Development Workflow

### Setting Up Development Environment

1. **Clone and Setup**:
   ```bash
   git clone <repository>
   cd cameodb
   cargo build
   ```

2. **Run Tests**:
   ```bash
   # All tests
   cargo test --workspace
   
   # Specific crate
   cargo test -p cluster_core
   cargo test -p storage_engine
   
   # Integration tests only
   cargo test --test integration
   ```

3. **Generate Documentation**:
   ```bash
   cargo doc --open
   ```

### Test Data Management

- All test data goes in `test_data/` directory
- Use test utilities in `tests/common/mod.rs`
- Tests automatically clean up after themselves
- Never commit test artifacts to git

### Code Quality

- Run `cargo clippy` before committing
- Use `cargo fmt` to format code
- Ensure all tests pass: `cargo test --workspace`
- Check documentation: `cargo doc --no-deps`

## Git Workflow

### What's Ignored

The `.gitignore` file excludes:
- `target/` - All build artifacts and generated docs
- `test_data/` - Test-generated files
- IDE files (`.vscode/`, `.idea/`)
- OS files (`.DS_Store`, `Thumbs.db`)
- Temporary and backup files

### What's Committed

- Source code (`.rs` files)
- Configuration (`Cargo.toml`, `Cargo.lock`)
- Documentation (`.md` files, inline docs)
- Tests and examples
- CI/CD configuration

### Commit Guidelines

1. **Atomic Commits**: One logical change per commit
2. **Clear Messages**: Describe what and why, not how
3. **Test Before Commit**: Ensure all tests pass
4. **Document Changes**: Update docs for API changes

## Getting Help

- Check existing documentation in `docs/`
- Look at inline documentation: `cargo doc --open`
- Review test examples for usage patterns
- Ask questions in issues or discussions
